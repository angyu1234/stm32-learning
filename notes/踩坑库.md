# 踩坑库

> 每遇到一个 bug 就记一条：**现象 → 排查过程 → 根因 → 解决**。
> 面试问「你遇到过什么难题、怎么解决的」，这就是你的弹药库 —— 而且是真实的，比编的答案可信得多。
>
> 格式要写全，尤其是「排查过程」：面试官关心的是你怎么定位问题，而不是你最后改了什么。

---

## 模板（复制使用）

```markdown
### [编号] 一句话描述问题

- **日期**：2026-XX-XX
- **场景**：在做什么的时候遇到的
- **现象**：具体表现是什么（报错信息要原文粘贴）
- **排查过程**：怎么一步步缩小范围的（这是最重要的部分）
- **根因**：真正的原因
- **解决**：改了什么
- **预防**：以后怎么避免
- **关键词**：面试时这个问题会挂在哪个知识点上
```

## 第 1 周

### 001 （示例）LED 完全不亮，代码看起来没问题

- **日期**：2026-XX-XX
- **场景**：用寄存器方式配置 PC13 输出
- **现象**：下载成功、程序正常运行，但 LED 毫无反应
- **排查过程**：
  1. 先用万用表量 PC13 引脚电平 —— 发现始终是高电平，没变化
  2. 上调试器打断点，单步执行配置代码，看寄存器窗口里的 `GPIOC_CRH` —— 值确实被改了
  3. 回头看 `RCC_APB2ENR`，发现 bit4 是 0 → **时钟没开**
  4. 确认代码里写的是 `RCC_APB2ENR |= (1U << 4)`，看起来对
  5. 突然意识到：这段配置代码写在 `MX_GPIO_Init()` **之后**，而 CubeMX 生成的代码里已经有一处对 `RCC_APB2ENR` 的整体赋值，把我置的位覆盖了
- **根因**：对寄存器做了整体赋值（`=`）而不是读-改-写（`|=`），把其它位清掉了
- **解决**：改成 `|=`，或把初始化顺序调整到最前面
- **预防**：**操作寄存器一律用 `|=` 和 `&=~`，绝不整体赋值**（除非确实要整体覆盖）
- **关键词**：RCC 时钟使能、寄存器读改写、CubeMX 生成代码的初始化顺序
